romsort

A sorted, verified LaunchBox library built from your existing ROM collection. No original file is ever moved or rewritten, and every LaunchBox path that worked still works.

  • Lua 5.1+ / LuaJIT
  • bash
  • No-Intro
  • Redump
  • LaunchBox
  • MIT
Get it on GitHubRun it

Why it exists

My games were spread over a LaunchBox install, a second drive full of PlayStation and PSP discs, and the dumps of three handheld SD cards: about a terabyte, with the same games in four places under four names. Every ROM manager I tried wanted to move or rename files. LaunchBox stores the exact path of every game, so that breaks it: a renamed file is a dead entry, and with ten thousand games you find out one at a time.

romsort leaves your collection alone and builds a second, sorted LaunchBox next to it.

What you get

sorted/LaunchBox/
  Games/Nintendo Game Boy Advance/Golden Sun (USA, Europe).gba
  Games/Super Nintendo Entertainment System/Chrono Trigger (USA).sfc
  Games/Nintendo Game Boy/Unverified/my hack.gb
  Games/Arcade/sf2.zip
  Data/  Images/  Emulators/  ...   your install, mirrored
  • Verified names. Every file is hashed with SHA-1, or CRC for files inside zips, with NES, Lynx, Atari 7800 and SNES copier headers stripped. It is then matched against No-Intro and Redump. Matches get their canonical name; card ROMs no database knows go to Unverified/.
  • No extra disk. The library is hardlinks into your sources. Deleting it frees nothing because it costs nothing, and you lose nothing.
  • One copy of each game. Identical files from different drives and cards fold into one entry. The LaunchBox copy wins its name.
  • LaunchBox keeps working. Every path in LaunchBox's XML is resolved and rewritten to the file's new home. That includes J:\ and P:\ drive paths and Windows names in the wrong case. Only the path text changes; every other byte of the XML is identical. Box art matches on titles, which never change.
  • Safe to re-run. Hashes are cached, so a rebuild only reads new files. A rebuild never overwrites anything you changed inside the sorted library.

The check that makes it safe

After every build, romsort check re-reads LaunchBox's XML from the original and from the sorted library, then compares them path by path. It fails the run if any of these is true:

  • a path that resolved in your original no longer resolves;
  • a path now points at different content;
  • either XML file differs anywhere outside a path value;
  • the original install changed while the run was reading it.

Some paths were already broken before romsort ran, like games on a drive that no longer exists. Those are left exactly as they were and listed in a report, so you can see what was missing all along.

What it never renames

  • Arcade sets (MAME, FBNeo, Neo Geo, CPS, Naomi), because emulators find a set by its zip name.
  • Multi-file discs: anything sharing a folder with a .cue, .gdi, .m3u or .ccd, so cue sheets keep finding their tracks.
  • Per-game folders inside a LaunchBox platform folder, and port or OpenBOR trees.

Run it

You need bash, coreutils, findutils, unzip and Lua 5.1 or newer (LuaJIT is fastest). 7z is optional; with it, .7z and .rar archives are matched too.

git clone https://github.com/Spaceghost/romsort && cd romsort
git clone --depth 1 https://github.com/libretro/libretro-database dats
cp config.lua my.lua                         # point it at your drives
ROMSORT_DATS=dats/metadat ./romsort plan  --config my.lua
ROMSORT_DATS=dats/metadat ./romsort build --config my.lua

plan is a dry run. It hashes, matches and writes a report, and puts nothing in the library. For a terabyte, start it detached and check back:

./romsort autostart on                 # once: resume after any reboot
./romsort start build --config my.lua
./romsort status                       # step, progress, ETA, result
./romsort ui                           # the same, live, in Neovim

Live in Neovim already? The checkout is a plugin too. Add it to runtimepath and :Romsort opens the dashboard in its own tab of your session, with :Romsort build, :Romsort status and the rest tab-completed.

Every hash is saved the moment it is computed, and every change to the library is atomic. An interrupted run therefore picks up where it stopped, and nothing that finished is redone.

CommandDoes
planScan, hash, match; write plan.tsv and report.txt. No library writes.
buildPlan, then create or update the library, then check it.
checkVerify the library against the original LaunchBox install.
startRun plan or build detached at low priority. It survives logout, and with autostart it survives reboots.
statusRunning, interrupted or idle; the current step, its progress and ETA; the report summary.
autostart onAdd a cron entry that resumes an interrupted run within 10 minutes, for example after a reboot.
uiLive dashboard in Neovim: windows for the run (step, progress bar, ETA), totals, the check and the log. Close it any time; the run carries on.
stopStop the detached run and forget it.

Configuration

The config is one Lua file. It lists your sources in precedence order, either LaunchBox-shaped <Platform>/ trees or card folders like GBA, FC or megadrive. It also says what each Windows drive letter maps to, and gives the platform table: LaunchBox names, folder aliases and DAT files. The sorted library must be on the same filesystem as the sources, because hardlinks can't cross filesystems.

romsort only organises files you already own. It downloads nothing but the public hash databases you point it at.
